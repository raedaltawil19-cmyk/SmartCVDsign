## Context

## 1. Base44 Conventions (Observed)

| Convention | Finding |
|---|---|
| `id` | Auto-generated by Base44. Never store manually. |
| `created_date` / `updated_date` | Auto-generated. Used as sort keys (`-updated_date`). Never written by app code. |
| `userId` | NOT stored explicitly. Base44 enforces per-user isolation at the platform level. No entity in this project stores a `userId` field. |
| JSON / nested objects | Used freely (`SavedCV.data`, `RepositioningAnalysis.result`). |
| Arrays in fields | Supported. Used in analysis result objects. Not indexable/filterable. |
| Scalar filter fields | `.filter()` requires flat scalar fields. Nested array filtering is not available. |
| Run/session tracking pattern | Separate entity per job: `RepositioningAnalysis`, `CourseDiscoveryRun`. |

## 2. Proposed Field Decisions for ProfessionalProfile

| Field | Decision | Reason |
|---|---|---|
| `userId` | **REMOVE** | Base44 provides isolation. No existing entity stores this. |
| `sourceCvIds` | **REMOVE** | Redundant. Already traceable via `ProfessionalEvidence.sourceCvId`. Grows unboundedly. |

| `professionalEvidence[]` | **MOVE** | To a separate `ProfessionalEvidence` entity (see §3). |

| `updatedAt` | **REMOVE** | Base44 provides as `updated_date`. |

## 3. One Entity or Two?

**Recommendation: Two entities (Option B).**

### Option A (embedded array) — rejected

- No server-side filtering on nested arrays in Base44.
- A heavy user (~100 master + ~500 tailored CVs) accumulates thousands of evidence items in one document.
- Read-modify-write required for every update — race condition risk.
- Document size limits become a risk at scale.

### Option B (separate ProfessionalEvidence entity) — selected

- Each evidence item is individually filterable: `.filter({ profileId, category })`.
- Profile document stays small (state only, not accumulation).
- Adding evidence = `create()` one record. No array mutation.
- Deduplication: `.filter({ profileId, observationId })` before insert.
- Phase 3B can query evidence by category, status, factId in a single indexed query.
- Each record has its own auto-generated `created_date` (auditability).
- Per-item lifecycle via `status` field.

## 5. Fact Identity vs Source Identity

**Problem:** The current `evidenceId` includes `sourceCvId`, causing the same professional fact from two CV versions to produce two unrelated IDs.

**Solution — two-level identity:**

```
factId        = hash(category | field | itemKey | stableStringify(value))
observationId = factId | sourceCvId | changeType
```

- `factId`: content-addressable. Same fact in 100 CVs = same `factId`. Enables Phase 3B to recognise facts confirmed across many versions.
- `observationId`: unique per specific occurrence. Used for dedup before insert.

This requires updating `buildEvidenceItem()` in `professionalEvidence.js` during implementation (Phase 3B).

---

## 6. Master vs Tailored Evidence Lineage

The three fields `sourceCvId`, `sourceType`, `sourceMasterCvId` are sufficient for full chain tracing:

```
Tailored CV (sourceCvId)
    ↓ sourceMasterCvId
Source Master CV
    ↓
Professional fact
```

`diffTailoredToSourceMaster()` already correctly limits extraction to genuine additions. No structural change needed.

---

## 7. Removals

**Recommendation: Option C — keep evidence, mark `status = inactive`.**

- `REMOVAL` creates a `ProfessionalEvidence` record with `status = inactive`.
- Existing `active` records with the same `factId` are updated to `status = inactive`.
- Evidence records are never deleted.
- Phase 3B reads `status = active` for the current profile; reads `status = inactive` for historical depth.
- Re-adding a skill in a later CV creates a new `FACT_ADDITION` record with `status = active`.

---

## 8. CONTENT_REWRITE

- Store `CONTENT_REWRITE` as evidence with `changeType = CONTENT_REWRITE`, `status = active`.
- `previousValue` captures the old wording.
- No additional boolean flag needed. `changeType` is sufficient.
- The 40% word-overlap heuristic in `cvDiff.js` stays untouched.
- **Phase 3B** decides semantically whether the rewrite is a refinement or a new fact.

---

## 9. ProfessionalProfile vs RepositioningAnalysis Boundary

**ProfessionalProfile** = what the user has done (facts/evidence).  
**RepositioningAnalysis** = what the user could do (career conclusions).

Must NOT be stored in ProfessionalProfile:
- Career path recommendations
- Job opportunities
- Skill gap analysis
- AI-generated career narratives

---

## 10. Processing State

`lastAnalyzedCvFingerprint` is insufficient. It cannot answer:
- Was a specific CV version processed?
- Did a tailored CV contribute evidence?
- Did an analysis fail mid-way?

**Recommendation: `ProfessionalProfileRun` entity** (following the `RepositioningAnalysis` / `CourseDiscoveryRun` pattern already in the project).

Skip already-processed CVs: `.filter({ profileId, cvFingerprint, status: "ready" })`.  
Retry failed runs by status.

---

## 11. Scale Estimate

| Source | Evidence items |
|---|---|
| 100 master CVs × ~15 items/diff | ~1,500 |
| 500 tailored CVs × ~5 genuine additions | ~2,500 |
| **Total** | **~4,000** |

4,000 individual `ProfessionalEvidence` records: safe, filterable, paginable.  
4,000 items embedded in one document: unsafe, unqueryable, at risk of size limits.

---

## 12. Security / User Isolation

Base44 enforces per-user isolation at the SDK level. No `userId` field needed. This matches all existing entities in the project. `profileId` provides secondary integrity at the application level.

## 14. What Phase 3B Will Consume

1. Read `ProfessionalProfile` (status, count).
2. Query `ProfessionalEvidence` filtered by `{ profileId, status: "active" }`.
3. Optionally filter by `category` for domain-specific analysis.
4. Group by `factId` — facts with multiple observations are stronger signals.
5. Weight `sourceType = "master"` evidence higher than `tailored`-only evidence.
6. Trace `sourceMasterCvId` for tailored evidence lineage verification.
7. Pass structured evidence to the repositioning agent as context (not raw CV text).
8. Write conclusions to `RepositioningAnalysis` only — never back to `ProfessionalProfile`.
